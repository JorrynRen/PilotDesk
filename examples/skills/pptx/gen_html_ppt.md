## 阶段二：演示文稿的实现
本阶段的目标，是把内容真正落地为可导出的 HTML 幻灯片：先固化视觉样式，再备好素材，然后按叙事结构组织大纲，最后逐页实现并校验导出。

---

### 第一步：写入设计 CSS
用户选定的风格方案还只是一套"设计意图"，本步要把它变成后续每页都能复用的**视觉样式**基础。

读取阶段一用户选定的风格方案（`<ppt-dir>/visual_exploration.md`）和场景分析结论（`<ppt-dir>/scenario_analysis.md`），在此基础上落实视觉样式。

思考要点：这套 PPT 的视觉签名是什么？哪些元素（标题、卡片、表格、图表区）需要统一风格？Bold Choices 中哪些可以抽象为 CSS 规则，哪些只能留给单页实现？

将结论写入 `<ppt-dir>/pages/design.css`，按以下顺序组织：
```
1. Reset          全局重置（固定内容，见下文）
2. :root          Design Token（CSS 变量）
3. 组件样式       .slide-title、.slide-body、.slide-card、.slide-table、.slide-chart 等
```
design.css不应当包含的内容：.slide-container,.slide-main页面布局容器。
**Reset（固定内容，禁止修改）**

`design.css` 第一段必须是以下 Reset 规则：
```css
/* === Reset === */
*, *::before, *::after {
  box-sizing: border-box;
  margin: 0;
  padding: 0;
}
body {
    font-family: <阶段一设定的字体方案>;
	font-weight: 400 ;
}
ul, ol {
  list-style: none;
}

a {
  text-decoration: none;
}
```

**Design Token**（`:root` 变量）须覆盖色板、字体、间距、圆角，作为后续所有 HTML 页的唯一样式来源。色板与阶段一选定方案一致，正文字号不得小于 22px（除非用户指定）：

| 变量 | 用途 |
|---|---|
| `--color-bg` | 页面主背景 |
| `--color-fg` | 主文字 |
| `--color-muted` | 次要背景 / 卡片底色 |
| `--color-accent` | 强调色 |
| `--color-border` | 边框 / 分割线 |
| `--font-display` | 展示字体（大标题） |
| `--font-body` | 正文字体 |
| `--space-page` | 页面边距 |
| `--space-block` | 块间距 |
| `--radius-card` | 卡片圆角 |

**色彩与对比度**：定义 `:root` 色板与组件颜色时须满足以下硬性规则：
  - **WCAG 对比度底线**：`--color-fg` / `--color-accent` 等与 `--color-bg` / `--color-muted` 的实际组合，对比度须 ≥ 4.5:1（正文、标题、数据均适用）。
  - **深色背景上的辅助文字**：禁止使用暗灰或深蓝；最暗仅可到 `rgba(255,255,255,0.6)` 或浅灰（如 `#94A3B8`）。
  - **色板气质**：主色搭配鲜明强调色，优于均匀分布的配色；避免陈词滥调（尤其白底紫色渐变）。

**组件样式**：标题、正文、卡片、表格、图表容器等常用元素的**外观**（颜色、字号、字重、边框、背景），class 使用 `slide-` 前缀；**不含** `display: grid/flex`、`grid-template-*`、`flex-*` 等布局属性。

**视觉母题**：贯穿全套 PPT 的视觉签名（如单侧粗边框、角部色带等），不写入 design.css，由各页在 `<style>` 块中实现，各页间须保持一致。

**Bold Choices 实现**：将选定方案的 3-5 个视觉承诺在各页 `<style>` 块中落实，不写入 design.css。无法统一抽象的效果，在 `<ppt-dir>/outline.md` 的“视觉补充”中标注具体需求。

### 第二步：演示素材准备
大纲定稿后再去找图，容易因图片不可用而整页返工。本步在大纲之前，把可能用到的图片和数据素材提前备好、评估清楚。
1. **素材获取**：按阶段一的**配图决策**和**用户意向**，逐张完成生图、搜索下载或数据整理。
- 正文配图决策为"禁用"则全程不生图/搜图；为"全局适用"则为多数内容页备图；为"按页酌情"则按"调研依据"为少数内容页备图。
- 生图前须阅读 `reference/image_prompting.md`。人物介绍、地图类、正式庄重场景优先纯 CSS，不强行配图。
2. **用户/文档图片本地化**：除生成的图片外，用户上传图片、源文档内部图片、用户直接给出的图片 URL 属于“真实素材”，应该下载到 `<ppt-dir>/assets/`，按 `img_<序号>.<ext>` 命名，**禁止**直接粘贴原始长链接。下载后逐张校验：文件非空且能识别为合法图片；校验失败的如实告知用户，禁止用占位图或生图偷偷顶替。
3. **再写入 `assets.md`**：所有候选素材经评估并落盘后，**统一**登记到 `<ppt-dir>/assets.md`。**禁止**在素材尚未获取完成时预先写入占位条目。

获取与评估每张候选素材时，须想清楚：
- **能不能用**：分辨率是否够、有无水印、主体是否完整
- **重心在哪**：主体偏左/偏右/居中等，这决定后续文字安全区的方向
- **怎么获取**：生图，还是用户上传的素材
- **色彩是否协调**：与 `<ppt-dir>/pages/design.css` 的色板是否冲突，是否需要遮罩

`assets.md` 登记规则：每张素材分配唯一资源 ID，路径须为**本地绝对路径**（文件已存入 `<ppt-dir>/assets/`）或**生图工具返回的远程 URL（用户上传的图片 URL 需本地化）**；不可用素材须标注"放弃"及原因，避免大纲引用后返工。

### 第三步：组织幻灯片大纲
内容不是按页堆砌，而是按阶段一确定的叙事结构，**把已有素材充分展开**——页数、每页信息量、拆合页，都应来自对素材与叙事的判断，而非套用固定骨架。

#### 动笔前：从素材出发做判断
写第一页大纲之前，先回到用户提供的全部材料（对话、附件、`scenario_analysis.md`）和通过联网搜索搜集到的资料，在心里完成一次素材盘点，回答：
- 这场演示**实际上有多少值得单独呈现的信息**？各自是论点、证据、案例、数据、流程还是对比关系？
- `scenario_analysis.md` 中，当前叙事各阶段的**观众以听为主还是以读为主**？以读为主的阶段，幻灯片需要承载更多可扫读的细节；以听为主的阶段，才适合大字与留白——**密度应随阶段变化，而非全篇统一压到最简**。
- 对着这些材料，演讲者若按叙事讲下来，**哪些内容只占半页会显得浪费、哪些硬塞一页会讲不清**？这直接决定拆页还是合页。
- 结构页（封面、结语等）之外，**内容页数量是否与素材体量相称**？材料丰富却页数偏少，通常意味着信息被过度压缩；材料单薄却页数偏多，则是在注水。

盘点结论不必单独成文件，但应体现在后续每一页的“核心内容”里。

#### 逐页编排
组织每一页时，先想清楚两件事：**演讲者在这页要达成什么，观众该如何接收这页的信息**。

每页须回答——这页在叙事中处于哪个阶段？演说意图是什么？观众以听为主还是以读为主？**本页这一个核心信息，需要多少支撑材料才能讲透**——能在一页内清晰传达则保留，讲不透则拆页，多个薄点彼此独立则考虑合页。若有配图，引用哪张资源、文字与图片如何配合？

**一页一核心信息**，指的是一个可被观众带走的完整想法，**不是**一句话或一条 bullet 的上限。一个想法可以包含结论式标题、若干支撑要点、关键数据或图表——判断标准是“讲者 + 幻灯片能否在这一页内把这个想法讲透”，而非“能写多短就多短”。

**核心内容应写到近定稿**：标题、要点、数据、图表意图都写出**具体文案**（含名词、数字、时间等），让第四步可以直接据此排版，而不是在 HTML 阶段才临时发挥或补充。若某页文字注定偏少（如 Hook、Call to Action），须在“视觉补充”中说明如何用版式与装饰撑起画幅——**少字是叙事选择，空白是设计失误**。

**章节过渡页一致性**：要么为所有章节设置过渡页，要么全部不设——禁止部分章节有过渡页、部分没有，否则观众会误读结构层级。

版式上，先分析内容的逻辑关系（并列 / 从属 / 对比 / 递进），用**自然语言**描述版面构图。相邻页有意拉开版式差异，避免连续多页同质。

#### 定稿前自检
大纲写完后，用以下问题过一遍——任一答“否”则回到对应页修订，而非进入第四步：
- 素材里**每一个值得讲的信息点**，是否都能在某页的“核心内容”中找到对应文案？
- 在“以读为主”的叙事阶段，是否出现了**标题 + 一句空话**、无数据无要点支撑的稀疏页？
- 页数与拆合页的决定，能否用**素材体量或叙事需要**说清理由，而非“惯例如此”？
- 文字偏少的页，是否已在“视觉补充”中交代如何填满画幅？

#### 写入 outline.md
将逐页大纲写入 `<ppt-dir>/outline.md`，每页至少包含：

| 字段 | 说明 |
|------|------|
| 类型 | 封面 / 目录 / 章节 / 内容 / 结语 |
| 叙事阶段 | 对应 `<ppt-dir>/scenario_analysis.md` 中的哪个阶段 |
| 演说意图 | 演讲者在本页要达成什么 |
| 观众接收方式 | 听 / 读 / 听+读 |
| 核心内容 | 近定稿文案：标题、要点、数据、图表意图等具体文字，第四步应直接据此排版 |
| 图片资源 | `<ppt-dir>/assets.md` 中的本地绝对路径或远程 URL，无图填"无" |
| 版式意图 | 用自然语言描述版面构图与信息分区，如“左文右图，文字占左侧”“居中章节标题 + 副标题” |
| 视觉补充 | （可选）该页特殊视觉处理或页面级样式需求；文字偏少时说明如何撑起画幅 |

所需图片若在第二步未搜集到，须回到第二步补充后再继续。

---

### 第四步：逐页生成 HTML
按 `<ppt-dir>/outline.md` 逐页实现，引用第一步的样式和第二步的图片资源。

**必须执行**：全文阅读 **`html_slide_technical_design.md`**（第一步已按色彩与对比度约束定稿 Token；本步落实布局与其余技术规范），将大纲中的“版式意图”落实为 Grid/Flex 布局，字号按内容块数量遵循其中的自适应规则；**非封面页**严格遵循全部技术规范。

阶段一已生成的封面 HTML 无需重做，用 Python 脚本复制到 `<ppt-dir>/pages/slide_01.html`（封面按 `gen_ppt.md`“封面页 HTML 技术规范”生成，原样复制即可，不要求引入 `design.css`）。其余页面使用 `file(brief=..., action=write, path=..., content=...)` 写入，**禁止**用 Python 脚本写 HTML。

单页节奏：
1. 内容页用 `<link rel="stylesheet" href="design.css" />` 引入 `design.css`；封面页（`slide_01.html`）已复制完成，无需修改。按大纲“视觉补充”在 `<style>` 块补充页面级样式
2. 将“版式意图”翻译为 HTML 结构（Grid 定骨架、Flex 分比例），兑现 Bold Choices
3. 写入前自检 `.slide-main` 的 CSS：
   - `grid-template-rows` 不能混用 `auto` 和 `1fr`
   - 同构并排块 `justify-content: flex-start`（不是 `center`）；末尾元素（若有）加 `margin-top:auto` 推至底部对齐
   - 其余项对照 `html_slide_technical_design.md`：grid 轨道对应、字号匹配、图片安全区、色彩对比度复检

---

### 第五步：跑版校验
所有 HTML 生成完毕后，调用 `check-layout` 检测合法性与跑版（通过服务端 API）。

**路径变量**：先用变量保存工作目录根路径，再拼接完整文件路径，避免命令行过长导致出错。

```bash
PPT_DIR="output/<ppt-dir>"

python "<技能根目录>\scripts\pptx_cli.py" check-layout \
  "$PPT_DIR/pages/slide_01.html" \
  "$PPT_DIR/pages/slide_02.html"
```
跑版一般不会花费太长时间。 如果命令进入了后台执行的状态， 建议每10s检查一次进程结果。
---

### 第六步：导出 PPTX
校验通过后，导出 PPTX：

```bash
PPT_DIR="<ppt-dir>/pages"
# 注意：slide_*.html 必须在引号外，否则 * 不会被 shell 展开
python "<技能根目录>\scripts\pptx_cli.py" html-to-pptx "$PPT_DIR"/slide_*.html -o "<ppt-dir>/<主题名>.pptx"
```
导出pptx一般不会花费太长时间。 如果命令进入了后台执行的状态， 建议每10s检查一次进程结果。

`<主题名>` 命名规则**：
- **语言一致性原则**：主题名的整体语境须与用户提问的主语言保持一致。中文提问用中文命名，英文提问用英文命名。
- **品牌名与专有名词处理原则**：保留官方/约定俗成称呼：对于知名的国外公司、品牌、技术名词（如 OpenAI、Tesla、Netflix、DeepSeek、Kubernetes 等），如果其中文市场没有公认的硬翻译，或者官方直接使用英文名，必须保留其原本的英文/专有名词形式，仅对后缀和描述部分进行翻译。严禁机械化生硬翻译：如将 OpenAI 翻译为“开放人工智能”。
